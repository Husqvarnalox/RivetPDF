# ADR-0001: C++23 as the language baseline

Status: Accepted

Date: 2026-09-24

## Context

Rivet is a native C++ desktop application whose core abstractions depend on
several language/library features that arrived across recent C++ standards:

- Fallible operations at subsystem boundaries should return a value-or-error
  type without exceptions. `std::expected<T, E>` (C++23) is the standard
  solution; C++20 has no standard equivalent, which would force a third-party
  dependency (`tl::expected`) or hand-rolled variants.
- The threading model uses a fixed worker pool with cooperative shutdown.
  `std::jthread` and `std::stop_token` (C++20) give automatic joining and
  stop-signal plumbing; the `TaskScheduler` worker loop is built on them.
- AppleClang 21 (current Xcode toolchain) supports the C++23 features Rivet
  relies on, including `std::expected`, `std::jthread`/`std::stop_token`,
  defaulted comparison operators, and `std::expected`-based templates.

The build already pins `CMAKE_CXX_STANDARD 23` with
`CMAKE_CXX_STANDARD_REQUIRED ON` and extensions off, and the top-level
`CMakeLists.txt` requires CMake >= 3.28.

## Decision

Rivet targets **C++23** as its language and library baseline.

- `Result<T>` (`rivet::core`) is defined as `std::expected<T, Error>`; the
  error model is standard-library based, no `expected` backport is vendored.
- Concurrency primitives are `std::jthread` / `std::stop_token`
  (`TaskScheduler`, `SerialExecutor`).
- The macOS compiler baseline is **AppleClang 21** (Xcode toolchain). MSVC
  and GCC support on Windows/Linux is planned but not yet the baseline.

## Consequences

- No third-party expected/result or thread-pool dependencies are needed for
  these facilities, keeping the dependency footprint minimal.
- C++23 is required of all compilers that build Rivet; older toolchains
  cannot compile the project. On macOS this means a current Xcode.
- Windows (MSVC) and Linux (GCC/Clang) builds must be validated against the
  same C++23 baseline when those ports begin.
- C++26 features remain out of scope until the standard and compiler support
  settle.

## Rejected alternatives

- **C++20**: lacks `std::expected`; would require a third-party expected
  implementation, which contradicts the minimal-dependency goal.
- **Stay on C++17**: loses `std::expected`, `std::jthread`/`std::stop_token`,
  and defaulted comparisons; would need substantially more hand-rolled
  infrastructure.
- **Wait for C++26**: no concrete benefit for current requirements; compiler
  support is not uniformly available across the planned platforms.
- **Third-party result/thread-pool libraries** (e.g. `tl::expected`,
  Folly): unnecessary once C++23 is the baseline; each dependency must
  justify itself.
